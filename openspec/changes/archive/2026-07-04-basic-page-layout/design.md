## Context

当前项目处于 V1 原型开发初期，需要快速验证主游戏场景的 UI 布局结构。通过搭建纯视觉的场景框架（无游戏逻辑），可以在早期确认：
- 各区域的相对大小和位置关系
- 棋盘格子的视觉尺寸
- 订单槽位的排列方式
- 底部控制栏的布局

技术栈：Godot 4.7，使用内置 UI 节点（Control、Container、Button 等）。

## Goals / Non-Goals

**Goals:**
- 创建完整的主场景层级结构（A/B/C 三区），比例符合参考图 `gameplay_scene.png`
  - A 区（顶部 HUD+ 订单）：约 28% 屏幕高度
  - B 区（棋盘）：约 52% 屏幕高度（最大区域）
  - C 区（底部控制栏）：约 20% 屏幕高度
- 每个容器和元件都有占位图片填充，可直观预览大小
- 棋盘区预创建 36 个 Button 节点，验证网格布局效果
- 场景可在 Godot 编辑器中直接打开预览

**Non-Goals:**
- 不编写任何游戏逻辑脚本（StaminaSystem、GridSystem 等）
- 不实现信号/EventBus 通信
- 不使用真实美术资源（用 ColorRect 或占位图代替）
- 不处理响应式布局/多分辨率适配（V1 固定分辨率）

## Decisions

### 1. 占位图片方案

**决策**：使用 Godot 内置 `ColorRect` + 不同颜色区分元件，而非外部图片文件。

**理由**：
- 零依赖，不需要额外资源文件
- 颜色区分直观（如 HUD 用蓝色、棋盘用绿色、订单用黄色）
- 后续替换为真实 TextureRect 即可

**备选方案**：使用程序生成的 Placeholder 纹理 — 过于复杂，ColorRect 足够。

### 2. 棋盘 36 个 Button 的创建方式

**决策**：在 `GridBoard.tscn` 中直接放置 36 个 `ItemCellButton` 实例，使用 `GridContainer` 自动排布。

**理由**：
- 符合用户"先验证美术效果"的需求
- 可视化编辑直观，可在编辑器中直接调整
- 后续可改为动态生成，但原型阶段效率优先

### 3. 场景文件组织

**决策**：主场景 `GameScene.tscn` 直接包含所有元件，不拆分为独立子场景。

**理由**：
- 原型阶段快速迭代，拆分过多反而增加维护成本
- 布局确认后再提取可复用组件为独立 `.tscn`
- 减少文件数量，便于早期调整

**备选方案**：每个元件独立 `.tscn` — 适合后期，但原型阶段过于繁琐。

## Risks / Trade-offs

- **[原型代码不可复用]** → 布局确认后需要重构为组件化结构，但早期验证价值大于重构成本
- **[36 个 Button 性能]** → 原型阶段可接受，正式版本改为动态生成
- **[固定分辨率]** → V1 目标分辨率 1080×1920（竖屏），后续需适配多分辨率
